# Куда и как поднять бэкенд (если Railway кончился)

Фронтенд на Vercel деплоится сам из `main` и от бэкенда не зависит.
Проблема всегда одна — **API и база**. Вся платформа это один файл SQLite,
поэтому хостинг обязан давать **постоянный диск**. Serverless (Vercel
Functions, Netlify, Cloudflare Workers) для этого бэкенда **не подходит** —
там нет диска, данные исчезнут при первом рестарте.

---

## 0. Сначала спасти данные ⚠️

Сделайте это **до** того, как удалите/отпустите старый сервис — вместе с
проектом Railway пропадает и том с базой.

1. Войдите в приложение под владельцем → **Центр управления → Бэкапы**.
2. **«Сделать бэкап»**, затем **«Скачать»** — получите файл `utir-*.db`.
   (Это же делает `GET /api/owner/backup/download`.)
3. Дополнительно: каждая команда может выгрузить свои данные —
   Настройки → экспорт (`GET /api/team/export`).

Файл `utir-*.db` — это **вся платформа**: команды, сделки, финансы,
настройки. Храните его как ценность.

Если Railway уже не отвечает — придётся оплатить минимальный период,
поднять сервис на несколько минут и забрать бэкап. Другого способа
вытащить данные с их тома нет.

---

## Вариант A. Продлить Railway — самый быстрый

Ничего не переносим: база на месте, переменные заданы, вебхуки настроены.
Оплатили → сервис поднялся → всё работает.

**Меньше всего риска сломать.** Переезд (вариант B) требует заново
перенести ~15 переменных и переподключить 4 внешних сервиса — каждый
шаг это шанс что-то уронить.

---

## Вариант B. Переезд на Render (готовый blueprint)

В репозитории уже лежат `Dockerfile` и `render.yaml` — сервис и диск
создадутся сами.

1. **Render → New → Blueprint** → выбрать этот репозиторий → Apply.
2. Render спросит секреты (те, что помечены `sync: false`) — возьмите их
   из Railway → Variables. Полный список и назначение: `docs/DEPLOY_ENV.md`.
3. Дождаться первого деплоя, проверить `https://<новый-адрес>/api/health` →
   должен вернуть `{"ok":true,...}`.
4. **Залить базу:** Render → сервис → Shell, и положить скачанный
   `utir-*.db` в `/data/utir.db` (мы монтируем диск именно туда).
   Проще всего — временно выложить файл по ссылке и `curl -o /data/utir.db <ссылка>`,
   затем перезапустить сервис. Пустой файл база создаст сама, но тогда вы
   стартуете с нуля.

> План `starter` платный — на бесплатном Render дисков не даёт, а без
> диска данные будут стираться при каждом деплое.

### После переезда обязательно обновить адреса

Новый адрес API ломает всё, что на него ссылалось:

| Где | Что поменять |
|---|---|
| **Vercel** → Environment Variables | `VITE_API_BASE_URL` = новый адрес API → **Redeploy** фронтенда |
| **Render** → Variables | `PUBLIC_API_URL` = свой же новый адрес (по нему WhatsApp забирает PDF), `APP_URL` / `CORS_ORIGINS` = адрес фронтенда |
| **Telegram** | вебхук перерегистрируется сам при старте, если задан `TELEGRAM_WEBHOOK_SECRET` |
| **Meta** (WhatsApp/Instagram) | вебхук в кабинете → `https://<новый-адрес>/api/webhooks/meta` |
| **Google / Facebook OAuth** | разрешённые callback-URL → новый адрес |

Проверка после переезда: вход в аккаунт, открытие сделки, отправка
сообщения в Чатах, ответ Telegram-бота.

## Вариант C. Свой VPS

Любая машина с Docker:

```bash
docker build -t utir-api .
docker run -d --name utir-api \
  -p 4010:4010 \
  -v /srv/utir-data:/data \
  --env-file .env \
  --restart unless-stopped \
  utir-api
```

Сверху нужен nginx с HTTPS (Let's Encrypt) — Meta и Telegram принимают
вебхуки только по HTTPS. Дальше тот же чек-лист адресов, что и в варианте B.

---

## Почему нельзя просто на Vercel

Бэкенд держит открытое соединение с SQLite, гоняет планировщики (утренние
сводки, бэкапы, напоминания об оплате) и хранит файл базы на диске.
Serverless-функции живут доли секунды, диска не имеют и планировщики в них
не работают. Переезд на Vercel означал бы переписывание хранилища на
внешнюю БД (Postgres) — это отдельная большая работа, не деплой.
